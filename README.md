# From a Biological Question to a Model You Can Defend

[![reproduce](https://github.com/ricchasethi/biological-question-to-data-science/actions/workflows/ci.yml/badge.svg)](https://github.com/ricchasethi/biological-question-to-data-science/actions/workflows/ci.yml)

Companion code for **articles 2 and 3** of *Research to Production - Data Science Biologist* (`https://research-to-production.beehiiv.com/`).

The question the whole analysis serves:

> **Can measurements taken from a breast tumour sample be used to distinguish a malignant tumour from a benign one?**

Article 2 turns that question into data you understand. Article 3 turns the data into a model, and then spends most of its time trying to break it.

Article 3 is organised around one idea: **a model is an experiment, so it needs controls.** You would not run an assay without a blank, a negative control and replicates. The notebook runs the equivalent four on the model, and reports them alongside the accuracy.

## Quickstart

```bash
# 1. An environment for this project alone
python3 -m venv .venv
source .venv/bin/activate                 # Windows PowerShell: .venv\Scripts\Activate.ps1

# 2. The exact packages that produced the published numbers
pip install --upgrade pip
pip install -r requirements.lock.txt

# 3. Make Jupyter use *this* Python, not some other one
python -m ipykernel install --user --name research-to-production

# 4. Get the data, and prove it is the right data
python -m src.fetch_data

# 5. Go
jupyter lab
```

**Two files, two jobs.** `requirements.txt` is the eight packages this project asks for directly —
that is the file to edit. `requirements.lock.txt` is what `pip` actually resolved: all 107 packages,
direct and transitive, at the versions the notebooks were run against. Install from the lock to
reproduce; edit the other, then `pip freeze > requirements.lock.txt`.

The versions are pinned on purpose. `pandas` records nothing about what ran; `pandas==3.0.5`
records what actually produced the result. A library upgrade can change a default, leave the code
running without error, and quietly move a published number. Upgrade deliberately: change the
version, reinstall, run the tests, and check the headline results before committing.

There is no `environment.yml` here, and that is deliberate. Conda and Bioconda earn their place when
a workflow needs tools `pip` cannot install — R, `samtools`, `bcftools`, aligners. This analysis is
pure Python, so a conda file would be a second environment to maintain and no extra reproducibility.
Let the problem pull the tool into the stack.

Open either notebook, switch to the **research-to-production** kernel (Kernel → Change Kernel), and run the cells top to bottom.

## The analysis without the notebooks

The notebooks are where the analysis is explained. They are not the only way to run it:

```bash
make            # get the data if needed, run the controls, then run the analysis
make verify     # check the raw data, touching nothing
make test       # the controls on the code, about 2 seconds
make run        # the analysis on its own, about 20 seconds, and writes a manifest
```

`make run` starts from `data/wdbc.data` every time, in a fixed order, and prints the same
report: the data, the model, the three controls, and the held-out test set. It has no memory
of anything you did earlier, which is the point - a notebook does.

It will not download anything, and it stops before it analyses anything if the raw data does
not match `data/checksums.sha256`. Quietly analysing a different file is worse than not
running at all.

## The controls: the data contract, and the tests

A laboratory does not trust a reagent because the tube has the right label on it. It runs a
control. The same two ideas apply to an analysis, and both live in this repository.

**The data contract** is `validate()` in `src/load_data.py`. It is the list of things this
analysis assumes about its input, written down as code rather than left in someone's head: 569
rows, the thirty columns in the right order, no missing values, no duplicate patients, nothing
negative, no nucleus with zero size, and a class balance inside the 30-45% malignant the model
was validated on. `make run` checks it before computing anything, reports *every* rule that
failed rather than just the first, and stops.

One rule is there because of the biology, and it is the reason this job needs a biologist:

> Thirteen samples record exactly **zero** concavity and zero concave points. A generic rule
> would call those missing values and drop or impute them. But a small, smooth nucleus has no
> detectable concave region, so zero is the correct reading. All thirteen are benign, and they
> are zero in all six concavity columns at once - never in only some. The contract accepts
> them, and rejects a batch where a *tenth* of the images say the same thing, because that is
> what a failed edge detector looks like.

**The tests** are the controls on the code:

```bash
make test
```

Twenty-one of them, in about two seconds. They check that the raw file is still the one the
articles were written from, that the column names are built in the order the file stores them,
that the contract accepts the real data and rejects six specific ways of being wrong, that the
scaler is inside the pipeline where it cannot leak, and that the published numbers - 97.3%
cross-validated, 96.5% held out, three cancers missed and one false alarm - still come out.

The last of those is the one that earns its keep. Upgrade a library, change a seed, refactor a
function, and the analysis will keep running and printing plausible numbers. The test is what
tells you a published number moved.

**The control patients** are the third layer, and the one that watches a single run rather than
the code. `src/controls.py` names three patients from the held-out set - the sample the model is
most sure is benign, the one it is most sure is malignant, and the borderline cancer it misses by
0.008 - and reads their probabilities on every run, to six decimal places:

```
CONTROL PATIENTS  (read on every run)
  859711   expected 0.000000   read 0.000000   ok
  915143   expected 1.000000   read 1.000000   ok
  879523   expected 0.491610   read 0.491610   ok
```

A test tells you the code is right. A control tells you *this run* was right. The borderline one
is the one that matters: a control at 0.0 and a control at 1.0 survive almost any change, but the
sample sitting next to the decision boundary moves as soon as anything upstream does.

## The run record: which run produced this number?

Six months from now someone will point at a figure and ask where it came from. "I ran the
notebook" is not an answer. Every successful run writes one into `results/`:

```
results/run-20260910T011622Z-d606af41.json
```

The name alone tells you when the run happened and, from the first eight characters of the input
checksum, which file it read. Inside, five sections say what produced the numbers:

| | |
| --- | --- |
| `input` | the data file and its SHA-256 - the same digest as `data/checksums.sha256` |
| `code` | the git commit, **and whether the working tree had uncommitted edits** |
| `environment` | Python version, platform, and the five packages that can move a number |
| `model` | `models/model.joblib` and its SHA-256; the same fit always hashes the same |
| `settings` | every seed, and the 0.5 threshold |

followed by the three control readings and the results themselves.

The `uncommitted_changes` field is the one people leave out. A commit hash recorded while the
working tree is dirty is a claim you cannot support: the code that actually ran exists nowhere
except that laptop.

The manifest is written **last, and only if the controls passed**. A run whose controls have
drifted prints its numbers, says so, and writes nothing - so a file in `results/` means a run that
was worth keeping. Nothing there is ever overwritten, and neither `results/` nor `models/` is
committed: the run records are yours, and the model is rebuilt by the pipeline that records its
checksum.

## Continuous integration: someone else's machine

The badge at the top of this file is the only claim in this repository that was not made by me.

`.github/workflows/ci.yml` runs on every push. A fresh Ubuntu machine checks out the repository,
builds the environment from `requirements.lock.txt`, and then runs the same three commands this
README tells you to run:

```bash
make verify     # is the raw data the file the articles used?
make test       # do the 21 controls still pass?
make run        # does the analysis run end to end?
```

That machine has none of the files I forgot to commit, none of the packages I installed by hand
two years ago, and no memory of anything I did in a notebook. **A CI runner is "someone else."**
If the analysis runs there, reproducibility is evidence rather than optimism.

Three details worth copying:

- **CI never downloads the data.** It runs `make verify`, not `make data`. A build that fetches
  from UCI on every push depends on someone else's server being up, and goes red for reasons that
  have nothing to do with your code. The data is committed, so this step is offline and instant.
- **There is no test matrix.** `requirements.lock.txt` pins all 107 packages for *one* Python
  version. Testing 3.11 and 3.13 as well would need a lock file each. Pinning and matrix testing
  are opposite bets, and reproducibility takes the first.
- **CI runs the README's own commands**, not a private set-up path. A workflow with its own
  bespoke steps proves the bespoke steps work. Running the documented ones proves the
  documentation is true, which is what a reader actually needs.

Every CI run uploads its manifest as a downloadable artefact. Those are the trustworthy ones: a
manifest written on a clean checkout records `"uncommitted_changes": false`, which no run on my
laptop can honestly claim while I am still editing.

| Package | Why | First needed in |
| --- | --- | --- |
| `pandas` | the DataFrame — tables with named columns and typed values | article 2 |
| `matplotlib` | every figure | article 2 |
| `jupyterlab` | the notebook interface | article 2 |
| `ipykernel` | lets Jupyter run code inside this environment | article 2 |
| `scikit-learn` | splitting, pipelines, logistic regression, cross-validation, the permutation test, metrics, PCA | article 3 |
| `scipy` | the t-tests and Mann-Whitney tests | article 3 |
| `pytest` | runs the controls on the code | article 4 |

If you set the environment up for article 2, you only need the last two - at the pinned versions:

```bash
pip install scikit-learn==1.9.0 scipy==1.18.0
```

Notebook 1 downloads with **`curl`**, which ships with macOS, virtually every Linux distribution, and
Windows 10 and later. `python -m src.fetch_data` does the same job without it, and verifies the
checksums afterwards.

Step 3 is the one people skip, and it produces the most baffling error in early data science: `ModuleNotFoundError: No module named 'pandas'` *immediately after* watching pip install pandas. Section 0 of each notebook ends with a cell that prints which Python is actually executing your code - check that first whenever an import mysteriously fails.

Both notebooks are committed with their outputs saved, so they read without running. Every random seed is fixed, so re-running reproduces the numbers in the articles exactly.

## Notebook 1 - `exploratory_data_analysis.ipynb`

From a URL to a dataset you understand, in seven short sections:

- **0. Set up your environment** - one virtual environment per project, and how to point Jupyter at it
- **1. Get the data** - download the zip from UCI, unpack it, check you got data and not an error page
- **2. Look at it before you load it** - `head`, `tail`, `wc`, `grep`, `cut`, `awk`, `sed`, and the documentation
- **3. Hello world, with real data** - read the file with plain Python before reaching for a library
- **4. First look in pandas** - supply the column names, load, check shape and dtypes
- **5. Summary statistics** - missing values, `describe()`, group means by diagnosis
- **6. Explore the biology in the data** - histogram, box plots, scatter, correlation matrix

Section 2 is the one most tutorials skip, and it is how you discover that this file has **no header row** and that field 2 is the diagnosis - neither of which is guessable.

**What it establishes**, and what notebook 2 depends on: malignant nuclei are larger, but *shape* separates the classes more sharply than *size*; the classes overlap heavily, so no single measurement can classify a patient; the columns differ in scale by a factor of 25,000; and `radius`, `perimeter` and `area` correlate above 0.99, so thirty columns are nowhere near thirty independent facts.

## Notebook 2 - `data_to_model.ipynb`

Seeing is not knowing. The notebook builds the model in the first three sections, then spends the rest running controls against it:

- **0. Set up** - two packages more than last time
- **1. Getting the data in, and what article 2 found** - reload, and recompute the six findings we build on. Why the file's column order is load-bearing, and why `X` is capital and `y` is not
- **A model is an experiment. Where are its controls?** - the four controls the rest of the notebook runs, and their bench equivalents
- **2. Is the difference real?** - Welch t-tests, Mann-Whitney, Cohen's *d*, confidence intervals, and Bonferroni correction. Why a p-value answers the least interesting of three questions, and why statistical significance is not separability
- **3. The first model** - logistic regression explained as the dose-response curve you already know. Stratified splitting, why standardisation is not optional, pipelines, and probabilities. Includes **one patient carried by hand** from raw measurements through standardisation, weights and the sigmoid to a probability of 0.974 - the whole model as thirty multiplications and one curve
- **4. Control 1 - the blank** - what score you get for doing nothing: 63.2% on the test split, the floor every later number is read against
- **5. Control 2 - the replicate** - the same pipeline scores 93.9% to 100.0% across 50 random splits. Stratified and repeated k-fold cross-validation as technical replicates, grid search inside CV, L1 versus L2 regularisation, `class_weight`
- **6. Control 3 - the negative control** - shuffle the diagnosis column and refit, a thousand times. **A model with nothing to learn still scores 59.7%, and the luckiest shuffle reaches 64.4%** - so anything below about 65% on this dataset is inside the range pure noise produces. Our 97.4% sits 25 standard deviations clear of it
- **7. Accuracy is not enough** - precision, recall, specificity, NPV, F1, ROC-AUC and average precision, all explained through consequences. **The three missed cancers named individually**, all sitting inside the benign/malignant overlap article 2 identified. A threshold sweep from 4 missed cancers to 0, and a confidence interval on the accuracy itself
- **8. Control 4 - the sham, and the two ways models lie** - overfitting demonstrated (three models score a perfect 1.000 on training data and are *worse* on new patients), then data leakage demonstrated: **5,000 columns of pure random noise reach 69.6% "accuracy"** when feature selection happens before the split. Plus duplicate samples across a split, and a control panel to check a model against
- **9. Do we really need all thirty features?** - feature selection inside folds, L1 keeping 14 of 30, and PCA finding that ten components carry 95% of the variance - with PC1 turning out to be nuclear shape irregularity
- **What I would put my name on** - the result stated properly: model, validation, performance with confidence intervals, **the four control readings**, threshold policy, consistency with the biology, and limits

**The headline result:** logistic regression on all 30 standardised features, cross-validated accuracy **97.3% ± 1.5%**, held-out test accuracy **96.5%** (95% CI 91.3-98.6) with 3 false negatives and 1 false positive in 114 samples.

**And the controls that make it believable:**

| Control | What it asks | Reading |
| --- | --- | --- |
| The blank | What does doing nothing score? | 63.2% (predict benign for everyone) |
| The replicate | How much does the score move on its own? | 97.3% ± 1.5% over 50 estimates |
| The negative control | What does *no signal* score? | 59.7% ± 1.5%, best of 1,000 shuffles 64.4%, p = 0.001 |
| The sham | Can the procedure invent a result? | 57.5% on 5,000 noise columns - below baseline, when done correctly |

The model takes four lines. Knowing whether to believe it takes the rest of the notebook.

The permutation test fits the model 5,000 times and is the slowest cell in the notebook - well under a minute if `n_jobs=-1` has several cores, a few minutes on a modest laptop.

## The data

The **Wisconsin Diagnostic Breast Cancer** dataset: 569 samples, one per fine-needle-aspirate image, one image per patient. 30 features - ten nuclear measurements, each reported as its mean across nuclei, its standard error, and its "worst" value (the average of the three largest). 357 benign, 212 malignant. No missing values.

These are measurements of **cell nuclei, not of the tumour**. A `radius_mean` of 17.99 is not an 18 mm lump; it is the average size of nuclei in a microscope image.

Section 1 of notebook 1 downloads it from the UCI Machine Learning Repository, dataset 17:

```
https://archive.ics.uci.edu/static/public/17/breast+cancer+wisconsin+diagnostic.zip
```

The extracted `wdbc.data` should be 124,103 bytes, sha256 `d606af41...`, md5 `c6dd5a2909808f3a901cf00cfd8dfff0`.
The full digests are recorded in `data/checksums.sha256`; check them at any time with:

```bash
sha256sum -c data/checksums.sha256      # or: python -m src.fetch_data --verify
```

**If the download fails** - UCI's servers are not always reliable - the two files are also served individually at the older path, which needs no unzipping:

```bash
# The raw files are read-only, so remove them before replacing them - deliberately,
# rather than by a re-run quietly overwriting them.
rm -f data/wdbc.data data/wdbc.names

BASE="https://archive.ics.uci.edu/ml/machine-learning-databases/breast-cancer-wisconsin"
curl -fLo data/wdbc.data  "$BASE/wdbc.data"
curl -fLo data/wdbc.names "$BASE/wdbc.names"

python -m src.fetch_data --verify        # confirms you got the same file the articles used
```

Only the *file* URLs resolve there; opening the folder above them in a browser returns a 404, which looks like a dead link and is not one.

**One source to avoid.** UCI also publishes a tidied `data.csv` for this dataset. Same 569 samples, but it has a header row, the columns are renamed `radius1`/`radius2`/`radius3`, and the diagnosis has moved to the last column. Nothing in these notebooks works on it unchanged.

This is a teaching set from one hospital in the early 1990s, with no patient context and no documented units. **Nothing here is for clinical use.** The model in notebook 2 is a teaching artefact, validated on 114 samples from one institution, and it has no claim to work on slides prepared anywhere else.
